## What was built or found (newest first)
### Swap and hibernate (docs: `ISO-INSTALL-TEST-2026-10-20.md`, last two sections)
* The installer's two swap choices ("no Hibernate" / "with Hibernate") set up hibernation **identically** (`resume=UUID=` on the kernel line, `resume` hook, `CanHibernate=yes`, Hibernate button on the sign-in screen); only the swap size differs (5.95 vs 8.37 GiB on the 3.8 GB VM). Cause: Calamares' `grubcfg` adds `resume=` for any swap partition.
* **Fixed 2026-10-20, pushed, installer part not yet proven in a real install:** new Calamares job `hibernatefix` (`zohara-profile/airootfs/usr/lib/calamares/modules/hibernatefix/`, after `grubcfg` before `bootloader`). For swap choices `none` and `small` (read from global storage `partitionChoices.swap`) it removes `resume=` and writes `/etc/systemd/sleep.conf.d/10-zohara-no-hibernate.conf` (`AllowHibernation=no` ...). Tested with a fake `libcalamares` only.
* **Fixed and proven:** Settings' hibernate check (`backend/hibernate.rs`, 9 tests) counts only the swap `resume=` names, never zram or the swap file; on the owner's laptop it now says "cannot hibernate" (resume partition 8.8 GiB < RAM 15.3 GiB; the old check said yes).
* **Open, serious:** in the VM, `systemctl hibernate` (what the Hibernate button runs) wrote the image but **never resumed** (5 of 5: cold boot, session lost, kernel `PM: Image not found (code -22)`), while `echo disk > /sys/power/state` resumed 4 of 5. Cause not found (header flags, zram, kernel command line, splash and `HibernateMode` ruled out). May be QEMU-specific. **Test on real hardware with work saved before trusting Hibernate.** The owner's laptop: resume partition 8.8 GiB, zram 7.7 GiB (prio 100), swap file 16 GiB (prio 10); systemd may choose the swap file or zram, which the udev initramfs does not look at.

### The VM rig (memory note `zohara-vm-rig-2026-10-20`)
`~/zohara-vm`: UEFI, 60 GB NVMe, KVM, 4 CPUs, 4 GB, no window. `run.sh [ISO]` (no ISO boots the installed disk), `vm.py` (shot, click, rclick, type, key, move, quit; typing can drop a key), `wheel.py N`, `drag.py x1 y1 x2 y2`, `hub.py` (serves `srv/` on :8001, results POSTed to `out/`; the guest reaches the host at 10.0.2.2). Test user `tester`, throwaway password, VM only. Never start `run.sh` twice (it breaks the QMP socket). Reading the disk from the host: `qemu-io -r -f qcow2 -c "read -v OFFSET N" disk.qcow2`; GPT part 3 start is in the entry at byte 1024+256.
Hidden test desktop on the host (no effect on the real screen): `dbus-run-session -- kwin_wayland --virtual --output-count 2 --socket NAME --xwayland --no-lockscreen --exit-with-session ./script.sh` with `WAYLAND_DISPLAY=NAME` (without `--socket` it talks to the real session); it cannot receive simulated clicks (KWin asks for permission), so click tests go in the VM.
