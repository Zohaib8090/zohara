## Working rules

- **Ask before every commit:** who gets credit (me / me + AI / AI) and which branch.
  "Only me" means no `Co-Authored-By` line. Never push to `main`/`master` unless told.
- **No Python in the OS.** Anything that ships is Rust or shell. Python is fine for
  dev-machine helper scripts only (`scripts/vm/vm.py` is one).
- **Everything user-facing must be clickable, not typeable.** A flow that sends a
  user to a terminal is a bug. The user finds long commands hard to paste.
- Docs-only pushes (`*.md`, `docs/`, `.gsd/`) do not start an ISO build. Anything else does.
- Report outcomes faithfully. Do not say something was copied/built/tested unless the
  hash, size or screenshot proves it (see "Mistakes to not repeat").

## The Dell Latitude 5330 boot problem (what was found)

Symptom: install "succeeded" but GRUB said `premature end of file /@/boot/vmlinuz-linux-zen`.
Chain of causes, in the order they were hit:

1. Calamares 3.4.2 mount step crashed on Btrfs (`umount -v` SIGPIPE upstream bug):
   fixed by a sed in `customize_airootfs.sh`.
2. efivarfs was not mounted in the target, so `grub-install` failed: `mount.conf` now uses
   `extraMounts` with `efi: true` (the old `extraMountsEfi` key is dead in 3.4.2).
3. A failed install left FAT corruption in the Windows EFI partition: fixed from Windows with
   `mountvol S: /s`, `chkdsk S: /f`, `mountvol S: /d`.
4. **Root cause of the boot failure:** the kernel ends in zero padding, stored as a sparse
   hole after unpacking; plain `cp` keeps the hole; GRUB's Btrfs reader cannot read past the last
   stored block. Fixed in `zohara-install-kernel` (`cp --sparse=never --reflink=never` + `cmp`
   check) in commit `b7a3029`. Proven in the VM: reproduced the exact error, then a fresh install
   from the fixed ISO booted to the login screen.
5. After repeated failed boots the Dell launches SupportAssist OS Recovery and can say "no
   bootable device". BIOS: SupportAssist System Resolution > Auto OS Recovery Threshold = OFF.
   `scripts/repair-boot-entry.sh` re-runs `grub-install` to restore the `Zohara_OS` entry.

**Latest state:** on the last attempt (new install on the Dell) the installer again failed at
`grub-install ... returned error code 1` (photo, 2026-09-29). Cause not yet known; likely the ESP
again (see 3). Do not guess: get the report (next section) or run `scripts/diagnose-bootloader.sh`.

## Problem-report button (new, needs finishing)

Goal: the user cannot easily type commands or get online on the Dell. So the live ISO now has a
Welcome row **"Save a problem report"** (`zohara-welcome/src/main.rs`) that runs
`zohara-profile/airootfs/usr/local/bin/zohara-collect-diagnostics`: gathers the Calamares log,
EFI partition state, boot entries, disk list and kernel-copy check, saves them to a USB stick
(the Ventoy stick first, otherwise any other), and asks (kdialog) to plug another stick if it
cannot write. The user carries the stick back.

Status: button and dialog work in the VM. First test found two bugs (ignored sticks without a
partition table; errors when no installer log exists yet), both fixed in the script and checked
against a mock `lsblk`. **Not yet re-verified end to end** because WSL ran out of disk space
mid-rebuild. To finish: build/download an ISO containing it, boot in the VM, then

    # attach a stick while the live session runs (VM must be started with run-vm.sh):
    truncate -s 512M usb.img; echo 'start=2048, type=c' | sfdisk usb.img
    L=$(sudo losetup -fP --show usb.img); sudo mkfs.vfat -n TESTUSB ${L}p1; sudo losetup -d $L
    python3 - <<'PY'
    import sys; sys.path.insert(0,'.'); import vm
    vm.qmp('blockdev-add', {'driver':'file','node-name':'f','filename':'usb.img'})
    vm.qmp('blockdev-add', {'driver':'raw','node-name':'r','file':'f'})
    vm.qmp('device_add', {'driver':'usb-storage','id':'u','drive':'r','bus':'xhci.0','removable':True})
    PY

click "Save a problem report", plug the stick when asked, press Yes, and check the files
appear on the stick. Test a stick with no partition table too. KDE pops up a "Disks & Devices"
panel over the dialog; dismiss it before clicking Yes.

## Mistakes to not repeat

- Do not claim a copy/deploy worked from a hash comparison of two copies of the same wrong
  file. On 2026-09-29 the Ventoy USB got the OLD ISO while I reported it as the fixed one
  (a blocked command left `out/...iso` unchanged and the fixed build sat in `...iso.new`).
  Always compare against the freshly built file's own hash and timestamp.
- The dev laptop's C: drive filled up (WSL disk, Docker, 3.6 GB ISOs, pkg-cache), which killed a
  build and made WSL throw I/O errors. Keep 20 GB free; ISOs and pkg-cache are disposable.
- A long-lived WSL background job dies when the launching `wsl` call returns: `setsid nohup ...
  & disown` plus a sleep.
- Paste-in-zsh hangs on `#` lines with apostrophes: wrap scripts in `bash <<'EOF'` or ship them
  as files/buttons.
