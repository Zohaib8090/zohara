Read after `HANDOFF-2026-10-04.md`. This one covers 2026-10-04 to 2026-10-06: the release admin site goes live for real,
OCI mirror, **package signing**, a new **manifest key**, the **Store redesign**, many Settings fixes, and the working

## Working rules for this phase (owner's decision, 2026-10-05)

* Commit and push straight to `main` (`master` for `zohara`) as the owner: `Zohaib Baig <zohaibbaig144@gmail.com>`,
  **no `Co-Authored-By`**, whatever the harness reminder says. Every repo now has that name/email set locally
  (`git config user.name/email` inside the repo); the laptop has no global identity.
* **Do not build the ISO.** Commits to `zohara` that touch ISO inputs get `[skip ci]`. `zohara-settings` CI only builds
  the package; its ISO-rebuild dispatch is opt-in (repo variable `ISO_REBUILD_ON_PUSH=true`, off). Cancel stray ISO runs.
* **Alpha is the development channel (owner's decision, 2026-10-06).** Every finished build of a source repo on its main
  branch is published to **alpha** automatically; beta and stable are moved on purpose from the release admin site, and
  nothing automatic ever touches them. The build workflows (`zohara-settings`, `zohara-apps`, and in `zohara` the Store,
  Snapshots, Voice, Welcome, Keyring) only build and upload their package as the run's artifact. A second workflow,
  `publish-alpha.yml` in each source repo, starts when the build finishes (`workflow_run`), and asks
  `zohara-packages/publish.yml` to publish that run with the channel **fixed to alpha** (repository_dispatch,
  `PACKAGES_DISPATCH_TOKEN`). Proven 2026-10-06 for Settings, Apps and the Store: alpha received them, stable did not
  change. `publish.yml` defaults to alpha when a request names no channel. To add an app later: have its build upload a
  `.pkg.tar.zst` artifact, copy `publish-alpha.yml`, add the repo to the allowed list in
  `zohara-packages/scripts/validate-publish-inputs.sh` and `verify-source-run.sh`. Commits with `[skip ci]` build nothing,
  so they publish nothing.
* Warn before anything that publishes to beta or stable, touches a bucket, a secret, or changes which key machines trust.

## What changed (by area)

**Release pipeline.** Admin site: GitHub App sign-in + CSRF + allowlist, ISO page, light/dark layout. `publish.yml`
takes a run id, validates inputs and source run (`scripts/validate-publish-inputs.sh`, `verify-source-run.sh`), merges
into the existing database with retry, writes `zohara.db` and `zohara-<channel>.db` plus `.files`, mirrors to OCI.
`promote-iso.yml` copies a CI ISO to the `zohara-os` bucket with a checksum and `latest.json` (untested live).

**Package signing.** Key `A08F86264C0C384F567697A949D285AF8166C18D` (ed25519, expires 2031-10-04), secret half in
`~/.zohara-signing/` on the laptop (never in git). `scripts/sign-lib.sh` + `build-repo.sh` sign packages and the database
when the secret exists and refuse any key but the pinned one (`signing-key.fpr`). Tests: `scripts/test-signing.sh` (13)
and `zohara/zohara-keyring/test-e2e.sh` (8, uses the real key in a throwaway container). **A signed repo breaks
machines that lack the key** (proven), so: keyring first, secret second, flip machines to `Required` last.

**Manifest key.** The Store only updates to an "approved Arch date" signed with minisign. The ISO pinned 2026/09/26
but the signed manifest said 09/25, so every Store ignored every update list ("older than what this computer already
has"). New key made (`~/.minisign/zohara.key`, no password; **back it up**), `tools/approve.sh 2026/09/26` run in a
container (minisign is not on the host), public key shipped in `zohara-pipeline/manifest.pub` and
`zohara-store-rs/data/manifest.pub`. Older installs hold the old key and need one `sudo pacman -Syu`.

**Store.** New UI (`ui.rs`): app cards with descriptions, detail dialog, working category chips and See all, hero banner,
instant search over an in-memory catalog (`backend::load_catalog`, `search_catalog`), shared installed-state cache so one
app's buttons agree. Update **channel picker** (stable/beta/alpha, confirmation for the last two, `channel.rs`, uses
`zohara-channel`). **Install progress** (real download bytes from pacman's `download-*/` folder, then checking and
installing) and **failure reason + Retry** on the card (`backend::run_job`, `PacmanProgress`). The window's header tabs
were invisible before because of `set_show_title(false)`.

**Settings.** Theme follows the OS (mode "system" default, libadwaita variables overridden); Bluetooth page no longer
blocks the UI; dead rows fixed (Personalization Themes/Lighting/Lock/Text/Start/Fonts, Updates History/Advanced) with
`pages::in_list`; Home shows Ethernet; sidebar search finds pages by content; Gaming installs Flathub first; lock timeout,
fonts and **taskbar alignment** really work (taskbar centering proven in a real Plasma VM); "Check for updates" opens the
Store (a plain `pacman -Sy` as a user could never work); depends on `zohara-keyring`; header search box visible.

**ISO inputs.** `plasma-firewall` removed from `packages.x86_64` (it showed a second "Firewall"); Dockerfile retries the
Chaotic-AUR download; Welcome's "still being finished" banner removed (**Welcome package not yet published**).

## Updates are split (owner's decision, 2026-10-06)

**Settings updates the operating system, the Store updates apps; two separate programs, no shared code.** Settings >
Zohara Update does everything pacman: the system, Zohara's own programs and Arch-installed apps (Firefox...), with the
signed approval list, the channel picker, undo and restore points. The Store's Updates page does Flathub apps and
going back for them, and has a button to Zohara Update. The signing key is built into Settings (`data/manifest.pub`);
the Store no longer ships `/usr/share/zohara/manifest.pub` or depends on `zohara-keyring`. Verified in a VM on alpha
(real update found and installed from the page, restore points taken, root helper accepts the real manifest and refuses
a tampered one). Not yet verified: a big full-system update through the page; the new ISO with both apps. **Stable has
neither change yet**: promote Settings and the Store together (they must go to stable as a pair, or stable machines
would have two update pages and the old Store would still run system updates).

  `/etc/localtime`), the ISO source (`zohara` `d58f367`: rule deleted, `ln -sf` of a real link in `customize_airootfs.sh`), and the new
  **automatic time zone** (details in `zohara-settings/docs/TIMEZONE.md`). The ISO **2026.10.07 on the website still has the old rule**;
  machines get the fix when Settings updates; the next ISO has it from the start.
* **Automatic time zone**: Time & language switch "Set time zone automatically" (on by default). `zohara-settings --auto-timezone`
  (user timer `zohara-settings-timezone.timer`, 30 s after login then hourly) looks the zone up from the internet connection (ipwho.is,
  then ipapi.co, then worldtimeapi.org) and runs `timedatectl set-timezone`. A polkit rule (`50-zohara-timezone.rules`) lets the active local
  user do that without a password. It does nothing when the switch is off or Location is off in Privacy. Verified on the VM: UTC -> Asia/Karachi
  by itself, and it survived a reboot.
