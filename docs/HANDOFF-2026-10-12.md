## Open items and plans

1. **Reviewer's live-mode problem (reported by a YouTube reviewer who ran an older ISO in a VM with 3 GB RAM):** live mode did not show pending updates and the apps stayed old after updating.
   Findings from the code: the ISO **compiles Settings from `zohara-settings` `main` (alpha) at build time and stamps it `0.1.0.<build time>`** (`Dockerfile` section 8), the Store, Welcome, Voice and Snapshots from the repo's own sources;
   so the ISO's versions are newer than stable's and the Update page says "up to date", and the ISO carries unreleased code. Hypothesis, **not proven**: the live system's writable space is a small RAM overlay
   (archiso default is probably 256 MB; no `cow_spacesize` is set in `efiboot/loader/entries/`), so updates there fail or are lost; nothing in Settings or the Store knows it is a live session (no archiso detection).
   Plan agreed in chat (not built): (a) detect the live session (`/run/archiso` or `archisobasedir` in `/proc/cmdline`) in Settings and the Store and replace update buttons with a clear "install first" message; (b) build the ISO from the **stable packages** (download from the stable release, `pacman -U`);
   (c) do **not** raise the live RAM space (3 GB machines would run out of memory). First step: boot an ISO in a 3 GB VM and measure (`df -h /`, the Update page, the Store's Updates tab).
2. **ISO pipeline** (proposed, not built): rebuild on a schedule or on important changes (keyring, installer, boot), not on every stable promotion; boot-test the ISO headless in CI; upload to the bucket as a candidate (repo secrets `OCI_ISO_PAR` and `OCI_PACKAGES_PAR` exist; ask the owner before using any bucket or secret); verify the public download and hash;

## How the release was done (repeat this)

1. Promote Settings: `gh workflow run publish.yml --repo Zohaib8090/zohara-packages -f source_repo=Zohaib8090/zohara-settings -f run_id=<Build & Publish run id> -f channel=stable`. The run id is the **Build & Publish** run of the commit, not the "Publish to alpha" run.
2. Build the ISO in CI: `gh workflow run build-iso.yml --repo Zohaib8090/zohara --ref master` (or push without `[skip ci]`). If it fails, read `gh run view <id> --log-failed`.
3. Download the artifact `zohara-os-x86_64` (4 GB). `gh run download` died once with a network timeout. What worked: a resumable `curl -C -` loop against `https://api.github.com/repos/Zohaib8090/zohara/actions/artifacts/<id>/zip` (ask for the 302 `Location` with `curl -sI` and the `gh auth token`; `gh api` follows the redirect itself and hides it).
   The zip holds one file, the ISO. The zip size equals the API's `size_in_bytes`. Check `sha256sum`.
4. Oracle: the CLI is **not installed system-wide**. It lives in `~/.local/share/oci-cli-venv` (linked at `~/.local/bin/oci`, created with `python3 -m venv` and `pip install oci-cli`, version 3.94.2). `oci session authenticate --region ap-mumbai-1 --profile-name zohara --tenancy-name zohaibbaig144`
   opens the browser; **the owner types the password**. The token lasts about an hour; the upload (`oci os object put ... --part-size 128 --parallel-upload-count 6 --no-overwrite`) takes about 15 minutes, so log in just before it.
5. Check the upload: object size equals the file, and the multipart md5 (compute 128 MiB part md5s, md5 of the concatenation, base64, `-<parts>`) equals the `opc-multipart-md5` header. Then download it again through the public link **with resume and retries** and hash it (a plain `curl | sha256sum` is cut short now and then: `OpenSSL SSL_read: unexpected eof`, and gives a wrong hash).
6. Update `SHA256SUMS` in the bucket (keep a line for each ISO that stays), then the website (`index.html` download section: file name, size, hash), push, and check the live page and the live files (compare `sha256sum` of the live file with the local one).
